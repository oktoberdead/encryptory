# LAN-мессенджер на базе Encryptory: план

Черновик архитектуры для случая: сервер свой, весь трафик ходит внутри WireGuard, участники — несколько доверенных людей и устройств. Windows и Android — браузерные клиенты.

## Что уже есть и что нужно

| Есть | Нужно добавить |
| --- | --- |
| Криптоядро: X25519 + HKDF + AES-256-GCM, контейнеры, отпечатки | Сессии (X3DH), ratchet — чтобы «утёк ключ ≠ читай всё» |
| Разовый обмен: скопировал текст → вставил → прочитал | Транспорт: куда-то надо это текст положить, чтобы доставилось само |
| Интерфейс на чистом вебе, работает на Windows и Android | HTTPS (иначе на Android WebCrypto выключен — см. ниже) |
| CLI для отладки и обмена файлами ключей | Модель устройств: у человека теперь телефон + ноутбук |

## Ограничение №1: secure context

**WebCrypto (`crypto.subtle`) доступен только в защищённом контексте.** Это `https://`, `localhost` и `127.0.0.1`. Обычный `http://192.168.1.50` или `http://10.8.0.5` — **не** защищённый контекст: `crypto.subtle` там будет `undefined`, и приложение не запустится (у Encryptory на этот случай есть явная диагностика «WebCrypto недоступен…»).

Отсюда следствие: **на Windows всё заведётся с двойного клика по автономному файлу, а на Android — нет.** Открыть локальный файл на Android неудобно, да и хранилище для `file://` ненадёжно (ключи не переживут перезагрузку). Значит, для двух клиентов нужен HTTPS-эндпоинт внутри локальной сети.

Два рабочих варианта (оба — один раз настроить на сервере):

1. **Caddy с внутренним CA.** Caddy сам выпускает сертификат на внутреннее имя (`messenger.lan`), корневой CA надо один раз поставить на каждое устройство (Windows: «Доверенные корневые центры», Android: «Установить сертификат → Сертификат CA»). Плюс — не нужен интернет.
2. **Let's Encrypt через DNS-01.** Сертификат на обычное имя (`msg.example.com`) выпускается без открытия портов наружу; внутренний DNS отдаёт это имя только внутри сети. Плюс — не надо ставить CA на устройства, доверие обычное.

HTTPS здесь нужен **исключительно** для доступа к WebCrypto и нормальной работе хранилища — сам шифр остаётся E2E-шным, сертификат не является частью защиты сообщений.

## Ограничение №2: версии браузеров

X25519 в WebCrypto появился недавно:

| Браузер | X25519 |
| --- | --- |
| Chrome / Chrome Android / Edge | 133+ |
| Firefox / Firefox Android | 130+ |
| Safari / iOS Safari | 17+ |
| Samsung Internet | 29+ |

Всё, что старше, — Encryptory откатывается на P-256 (он поддерживается везде и читается по-прежнему). Нюанс: **устройства разных кривых друг с другом говорить не могут** — обмен идёт только внутри одной кривой, и утилита теперь честно об этом говорит вместо «каши» на выходе. Если у кого-то из близких старый телефон, проще всем держать ключи P-256, либо обновить браузер.

## Передача ключей: да, через SSH внутри туннеля

Короткий ответ: **можно и нужно**. SSH внутри WireGuard — это аутентифицированный и шифрованный канал, лучший из доступных для этой задачи.

Что важно различать:

- **Публичные ключи** — передавать можно любым способом: `scp`, `ssh cat`, файлошара, мессенджер, QR-код. Они публичны по определению.
- **Приватный ключ человека — не передавайте между людьми.** У каждого он свой, сгенерирован у себя.
- **Между своими устройствами** (свой ноутбук ↔ свой телефон) копировать приватный ключ уже осмысленно, но это компромисс: одно устройство скомпрометировано → вся переписка в обе стороны. Схема «ключ на устройство» лучше, но требует механизма доверия между устройствами одного человека (cross-signing). Для 3–5 человек это решается один раз копированием отпечатка; подробнее — в разделе про модель устройств.

Практический момент, который стоит учесть: если публичные ключи раздаются **не через релей**, а по SSH, то релей вообще не участвует в выборе ключей и не может подсунуть свои. Это сильно чище, чем «доверься серверу за ключами»: сервер остаётся тупым транспортом для шифротекста. Рекомендую именно так.

Ещё два правила, которые дешевле соблюсти сразу:

- **Проверяйте отпечатки** при первом обмене (даже по SSH — `ssh-keygen -lf` никто не отменял). Отпечаток — единственный детектор подмены.
- **Pin (TOFU)**: приложение должно запоминать «первый увиденный ключ» собеседника и кричать, если ключ вдруг изменился. Иначе подмена релея/канала пройдёт незамеченной.

## Топология

```
Внешний мир ──► роутер (Xray, WireGuard, публичный IP)
                   │
                   ├── wg0: 10.8.0.1
                   │     ├── ноутбук Windows   10.8.0.11
                   │     ├── телефон Android    10.8.0.12
                   │     └── устройства близких …
                   │
                   └── локальные машины без WG: 192.168.1.x
                           (для них сервисы доступны как обычно)
```

Правила, которые надо соблюсти при развёртывании:

1. **Релей слушает только на wg0** (`10.8.0.1`) и, при желании, на LAN-адресе. Никогда — на внешнем интерфейсе и никогда на `0.0.0.0`. Даже «только внутри VPN» удобнее сделать явной привязкой, а не надеждой на правила файрвола.
2. **Xray не должен трогать эту сеть.** В его конфиге исключите внутренние диапазоны (`10.0.0.0/8`, `192.168.0.0/16`, `fc00::/7`) из проксируемых — иначе трафик мессенджера поедет через внешний прокси, что полностью убивает смысл.
3. **PSK в WireGuard включите** — он подмешивается в рукопожатие и не ломается алгоритмом Шора (симметричные 256 бит ⇒ ~128 бит постквантовой стойкости). Храните его отдельно от конфига.
4. **Изоляция пиров.** По умолчанию WG-пиры видят друг друга. Если это не нужно — запретите peer-to-peer через `iptables` на wg0 и пропустите только трафик к сервису.
5. **DNS.** Внутреннее имя должно разрешаться только внутри (`10.8.0.1` как DNS). Публичного резолва у него быть не должно.
6. **Резервные копии.** Приватные ключи участников — на своих устройствах (файлом), не на сервере.

## Модель устройств (Windows + Android на человека)

У человека теперь два (и больше) устройства. Варианты:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Один ключ на человека, копия файла на его устройствах** | Просто, ничего не надо менять в формате | Компрометация любого устройства = компрометация всего; нет отзыва конкретного устройства |
| **Ключ на устройство + cross-signing** | Нормальная безопасность и отзыв | Нужен механизм «это устройство того же владельца» (у Signal — связка через уже доверенное устройство / QR) |
| **Ключ на устройство, без привязки к человеку** | Совсем просто: каждое устройство = отдельный участник | Отправитель должен знать все устройства адресата и раскладывать всем |

Для 3–5 человек в пределах LAN практичный путь: начать с первого варианта (быстро, привычно), а при желании — перейти ко второму через QR-связку «ноутбук ↔ телефон» один раз. Третий вариант не советую: он перекладывает знание о чужих устройствах на пользователей и ломается при каждой новой железке.

В любом варианте нужен **fan-out**: сообщение шифруется отдельно для каждого устройства-получателя. Это не протокольная деталь, а следствие асимметричной схемы — у каждого устройства свой публичный ключ, «одна посылка на всех» невозможна (это и хорошо).

## Релей: минимальный контракт

Держать его тупым. Три задачи: отдать очередь своим, принять входящее, разбудить онлайн-устройство.

```
POST /auth          → device token (доверенные устройства из белого списка)
GET  /key/:device   → публичный ключ устройства (или ключи раздаются по SSH)
PUT  /keys          → опубликовать / обновить свой публичный ключ
POST /send          → { to: [deviceId], blob: <шифротекст> }   сервер видит только шифротекст
GET  /inbox?since=  → забрать накопленное (для офлайна: пока устройство спало)
WS   /live          → пуш при появлении нового блоба
```

Правила: `blob` — непрозрачные байты; TTL на сообщения (например, 30 дней); лимит размера и квоты; никакой расшифровки и никаких «а зачем»; идентификатор устройства — не телефон, а сгенерированный ключ/токен. Сервер — единственное, что видит метаданные (кто кому и когда), и он свой, поэтому это приемлемо.

**Всё, что релей знает о содержимом, — длина.** Длину можно выровнять паддингом до размерных «корзин» (например, кратно 512 байтам), если хочется скрыть и её.

## Что реально не будет работать в браузере на Android

Честно, чтобы не строить ложных ожиданий:

- **Фоновые доставки нет.** Браузер не держит WebSocket, когда приложение свёрнуто, а Web Push требует выхода в интернет к push-сервису (Google/Mozilla) — внутри VPN он не заработает, и это ещё и утечка метаданных наружу. Значит: сообщения дойдут, но «уведомление о новом сообщении» — только пока приложение открыто (или в фоне недолго). Для надёжного фона на Android нужен нативный клиент или обёртка (Capacitor/Tauri) с foreground-сервисом.
- **Хранилище может быть вычищено.** Android освобождает место и может вытеснить данные браузера. Ключи надо уметь восстанавливать из файла/QR, а не полагаться на IndexedDB как на единственное место.
- **Копирование в буфер из фона** ограничено — не строить на этом протокол (это никак не влияет: у нас сообщение само приходит, копировать ничего не надо).

Вывод: **Windows — полный клиент из браузера; Android — рабочий клиент для «открыл, прочитал, ответил», но не «всегда в кармане с пушем».** Если нужен второй вариант, это отдельный нативный проект.

## Что стоит сделать до мессенджера

Небольшие вещи, которые полезны уже сейчас и нужны потом:

1. **Паддинг текста** до одинаковой длины — чтобы длина шифротекста не выдавала длину сообщения.
2. **Pin (TOFU) ключа собеседника** в интерфейсе с явным предупреждением при смене.
3. **Мультиполучатель**: шифрование одного текста сразу на несколько публичных ключей (прообраз fan-out).
4. **Очистка буфера обмена** по таймеру и «паник-кнопка» — мелочи, которые снижают цену ошибки.

## Дорожная карта

| Шаг | Что делаем | Результат |
| --- | --- | --- |
| 1 | Релей (Node, без зависимостей) + HTTPS через Caddy + PWA-манифест | Уже можно переписываться в пределах LAN, ключи — по SSH |
| 2 | Сессии: X3DH + Double Ratchet (библиотекой) | Forward secrecy, «утёк ключ ≠ читай всё» |
| 3 | Мультиустройство, QR-связка, отзыв устройства | Телефон и ноутбук сосуществуют без копирования ключей |
| 4 | Группы (sender keys → MLS), sealed sender, паддинг | То, что обычно называют «мессенджер» |
| 5 | Постквантовый гибрид X25519 + ML-KEM (WASM) | Защита off-line-записи от будущего квантового противника |

Порядок неслучаен: шаг 1 даёт работающую вещь сразу и не требует менять криптографию, шаг 2 — самый важный по безопасности и самый опасный для самодеятельности (ратчет пишем не сами).
