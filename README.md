# 🔐 Encryptory

Мини-приложение для шифрования текста между двумя людьми: **вы вводите текст — получаете «кашу», собеседник прогоняет её через ту же утилиту у себя и читает исходный текст**. Ключи при этом по сети не ходят, канал связи может быть любым — хоть открытый чат.

Криптография целиком в браузере (WebCrypto). Никаких сборщиков, зависимостей и бэкенда: три файла — HTML, CSS, JS.

```
Алиса                                                    Боб
──────                                                   ────
своя пара ключей (публичный + приватный)      своя пара ключей
        │                                              │
        └──── публичный ключ ──── лично/что угодно ────► │
        │                                              │
   ECDH + HKDF ──► общий секрет ◄───────────────────────┘   (одинаковый у обоих,
        │                                                    по сети не передаётся)
        ▼
txt ──► AES-256-GCM ──► «каша» ──► любой канал ──► AES-256-GCM ──► txt
```

## Быстрый старт

**Вариант 1 — просто открыть файл.** В репозитории лежит автономная сборка `dist/encryptory-standalone.html`: в ней страница, стили и код в одном файле. Двойной клик — и всё работает, в том числе офлайн, без всякого сервера.

**Вариант 2 — исходная версия из `index.html`.** Она тоже открывается двойным кликом (никаких модулей и запросов к серверу), но через сервер надёжнее: некоторые браузеры строже относятся к `file://` и буферу обмена.

```bash
npm run serve          # python3 -m http.server 4173 --bind 0.0.0.0
# затем http://localhost:4173
```

**Вариант 3 — терминал** (тот же формат, что и в браузере):

```bash
npm run cli -- keygen --name alice
npm run cli -- keygen --name bob
npm run cli -- encrypt --key alice-private.txt --to bob-public.txt --text "встречаемся в 21:00"
npm run cli -- decrypt --key bob-private.txt --in message.txt
```

## Как этим пользоваться

1. **Каждый создаёт свою пару ключей** на своей стороне (кнопка «Создать мою пару ключей»). Приватный ключ остаётся у хозяина, публичный можно отдавать кому угодно.
2. **Обменяйтесь публичными ключами.** Можно AirDrop'ом, флешкой, QR-кодом или в мессенджере — но обязательно **сверьте отпечаток** (короткая строка вида `K3PQ-7V2M-4HHV-…` под именем ключа). Если ключ подменят, отпечаток не совпадёт, и вы это увидите до того, как что-то отправите.
3. **Отправитель** вставляет ключ собеседника, пишет текст и жмёт «Зашифровать для собеседника». Получается бронированный текст:

   ```
   -----BEGIN ENCRYPTORY MESSAGE-----
   em2.BYVxNn0Pknx5sRg7O9xUhrT3nC5yYb2F…hkWuszU8cc40OkbeznkagCnaHwUmNmyRk5EjHP…
   -----END ENCRYPTORY MESSAGE-----
   ```

   Его можно отправлять по любому каналу.
4. **Получатель** вставляет шифротекст, жмёт «Расшифровать» — и читает текст. Свой приватный ключ при этом никуда не отправляется.

### «Локальная проверка»

Отдельная кнопка в блоке шифрования — для отладки и проверки работоспособности на этом же хосте. Она шифрует текст **дважды** и тут же расшифровывает обе посылки:

| Проверка | Что доказывает |
| --- | --- |
| Самому себе: зашифровать своим публичным ключом, прочитать своим приватным | Ваш ключ работает с обеих сторон |
| Временному «двойнику»: зашифровать одним ключом, прочитать другим | Реальный обмен между разными ключами проходит целиком |
| Посторонний ключ пробует прочитать посылку | Должен получить отказ, а не мусор |
| Исходный текст ищется в шифротексте | Не должен угадываться |

«Двойник» — временная пара ключей, которая живёт только в этой вкладке и тут же уничтожается. Проверочный шифротекст можно посмотреть в сворачиваемом блоке, но отправлять его никому не нужно.

> Свою посылку **собеседнику** расшифровать локально нельзя, и это не баг: для неё нужен приватный ключ адресата, а он есть только у него. Именно в этом и смысл асимметричного шифрования.

### Самопроверка

Кнопка «Самопроверка» в шапке (или `npm test`, или `node tools/cli.mjs selftest`) генерирует три пары ключей прямо сейчас и прогоняет полный цикл: шифрование → расшифровка, чужой ключ, порча шифротекста, подмена ключа отправителя и nonce, парольная защита ключа, большие тексты, совместимость со старой кривой. Ничего не сохраняется — можно смело жать.

## Что под капотом

| Шаг | Что происходит |
| --- | --- |
| 1 | Каждая сторона генерирует пару ключей **X25519** (32 байта на публичный ключ) |
| 2 | Стороны обмениваются **только публичными** ключами |
| 3 | Общий секрет = `мой приватный × его публичный` (ECDH) — одинаковый у обоих, по сети не идёт |
| 4 | Из секрета выводится одноразовый ключ через **HKDF-SHA256**; в `info` зашиты название кривой и оба публичных ключа, поэтому чужой ключ или ключ с другой кривой не подойдёт |
| 5 | Текст шифруется **AES-256-GCM** (аутентифицированное шифрование) со случайными солью и nonce на каждое сообщение |

Схема гибридная, как в TLS/PGP: асимметрика нужна только чтобы договориться о симметричном ключе, а сам текст шифруется быстрым AES.

**Что даёт GCM:** если шифротекст испортили в пути или он зашифрован не для вашего ключа, вы получите понятную ошибку, а не «мусор» на выходе. Молча подделать сообщение нельзя.

### Форматы контейнеров и ключей

| Что | X25519 (актуальный) | ECDH P-256 (старый, читается) |
| --- | --- | --- |
| Сообщение | `em2.<отправитель>.<соль>.<nonce>.<время>.<шифротекст>` | `em1.…` |
| Публичный ключ | `epk2.<base64url>` | `epk1.<base64url>` |
| Приватный ключ | `ek2.<base64url(pkcs8)>` | `ek1.…` |
| Приватный под паролем | `ek2p.<base64url(AES-GCM(PBKDF2-SHA256))>` | `ek1p.…` |

Пять первых полей контейнера подписаны как `additionalData` для AES-GCM — то есть защищены от подмены вместе с телом. Кривая определяется по префиксу: утилита сама понимает и новые, и старые контейнеры. **Обмен возможен только внутри одной кривой** — если ключи на разных кривых, вы получите понятную ошибку с подсказкой, а не «кашу» на выходе.

Приватный ключ по желанию защищается паролем (PBKDF2-SHA256, **600 000 итераций** — рекомендация OWASP 2025, соль 16 байт). Пароль не хранится нигде и восстановлению не подлежит.

## Модель угроз: что схема держит, а что нет

Для разовой посылки при условии, что ключи не утекают и обмен публичными ключами был сверен глазами:

| Атака | Исход |
| --- | --- |
| Прослушивание канала, запись трафика | Не прочитает. ECDH X25519 ≈ 128 бит стойкости |
| Правка шифротекста или заголовка (подмена отправителя, времени, nonce) | Обнаруживается: AES-GCM + AAD по всем полям |
| Подделка сообщения «от чужого имени» | Невозможна без приватного ключа — тег GCM не сойдётся |
| Перебор ключа | Атакуют не стойкость примитивов, а реализацию, ключи и endpoints |

Чего у схемы **нет** (это важно знать до того, как использовать её для чего-то серьёзного):

- **Forward secrecy отсутствует.** Ключи долгоживущие, ECDH симметричен: утёк один приватный ключ — читается вся переписка этого человека, включая старую записанную. «Собирай трафик сейчас, укради ключ потом» работает без всяких квантовых компьютеров.
- **Нет защиты от подмены ключа сервером/каналом.** Если собеседнику подсунут чужой публичный ключ, шифрование «сработает», но читать будет не тот. Единственный детектор — сверка отпечатка по независимому каналу.
- **Replay возможен.** Пересланная заново старая посылка расшифруется снова и будет выглядеть валидной.
- **Метаданные открыты.** Кто, когда, какого размера и как часто — всё видно в канале, плюс в контейнере открыто лежит публичный ключ отправителя (это стабильный идентификатор: по нему строится граф связей).
- **Квантовый компьютер** со временем сломает X25519 (Shor). AES-256 останется ~128-битным. Для постквантового E2E нужен ML-KEM — в WebCrypto его пока нет, потребуется WASM-сборка.
- **Endpoint — самое слабое место.** Утёк приватный ключ = конец истории. Ключ заперт в контексте страницы: XSS, вредоносное расширение или подменённый сервером бандл забирают его вместе с возможностью читать. Приватный ключ без пароля — отдельный риск.

Этих свойств достаточно для «передать текст по недоверенному каналу». Недостаточно для мессенджера с историей — там нужны X3DH + Double Ratchet (см. ниже).

## Развёртывание внутри WireGuard

Если сервер уже есть и весь трафик ходит внутри WireGuard, модель меняется сильно — и в основном в лучшую сторону:

- **Снаружи не видно ничего.** Никакого интернет-периметра: нет публичных портов, нет TLS-терминации, нет сканеров. ISP и внешний наблюдатель видят только «клиент общается с VPN-сервером».
- **Транспорт сам по себе end-to-end.** WireGuard использует эфемерные ключи на сессию (ротация ~2 минуты), поэтому статический ключ, украденный сейчас, не расшифровывает записанный ранее трафик. Это лучше, чем статическая схема Encryptory.
- **Аутентификация устройств** уже есть — по ключам WireGuard.

Но есть три места, где WireGuard **не подменяет** прикладное шифрование:

1. **Тот, кто завершает туннель, видит открытый текст.** Если сообщения складываются на сервер (store-and-forward, чтобы писать офлайн-получателю), приложение на сервере расшифровывает трафик и читает всё. Шифрование на уровне приложения (эта утилита) нужно именно там.
2. **Плоская сеть.** Добавили друга в VPN — он внутри периметра: видит другие пиры, часто и их подсети. Утечка конфига с приватным ключом (а он лежит в `/etc/wireguard/*.conf` и попадает в бэкапы) = возможность выдать себя за это устройство. Лечится роутингом (`AllowedIPs` на конкретный адрес, запрет peer-to-peer через `iptables`) и отдельным интерфейсом на каждую группу.
3. **PSK в WireGuard стоит включить.** `PresharedKey` подмешивается в рукопожатие и не ломается алгоритмом Шора (симметричный ключ 256 бит ⇒ ~128 бит постквантовой стойкости). Это дешёвый щит против «записали трафик сегодня, расшифровали после появления квантового компьютера» — при условии, что PSK не лежит рядом с конфигом.

Практический вывод: **WireGuard — отличный транспорт и аутентификация, уровень приложения — по-прежнему нужен.** Для дружеской группы «сервер свой, доверяем себе, не доверяем интернету» такая связка вполне рабочая.

## Если делать мессенджер

Encryptory — это «шифрование конверта». Мессенджер — это протокол сессий, доставка, мультидевайс и метаданные; криптоядро тут самая лёгкая часть.

Обязательный минимум поверх этой базы:

1. **X3DH** — асинхронный старт сессии: identity-ключ (X25519/Ed25519), signed prekey, пачка one-time prekeys, лежащих на сервере. Позволяет писать офлайн-получателю и даёт forward secrecy уже на этапе установки.
2. **Double Ratchet** — DH-ратчет на смену направления + симметричная цепочка на каждое сообщение. Превращает «утечка ключа = вся переписка» в «утечка = текущая сессия, которая сама заживает после обмена».
3. **Счётчики и дедупликация** — против replay и переупорядочивания.
4. **Сверка ключей** — safety numbers/QR, в идеале с transparency log, чтобы сервер не мог молча подменить ключ.
5. **Мультидевайс** — ключ на устройство, линковка и отзыв потерянных.
6. **Группы** — sender keys (проще) или **MLS (RFC 9420)**.
7. **Метаданные** — sealed sender, паддинг размеров, батчинг. «Печатает…» и галочки доставки выдают больше, чем шифротекст.
8. **Клиент** — non-extractable `CryptoKey` в IndexedDB, строгий CSP без сторонних скриптов, а лучше нативная оболочка (Tauri) с ключами в системном keychain.

> **Ратчет руками не пишите.** Примитивы просты, а стейт-машина — нет, и баги в ней (порядок ключей, пропуски, состояние при рестарте) съедают всю пользу. Берите проверенное: libsignal (Rust), mls-rs, openmls.

Для постквантовой версии E2E позже понадобится гибрид X25519 + ML-KEM: в `SubtleCrypto` ML-KEM пока нет (проверено), так что нужен WASM-биндинг (liboqs/PQClean).

## Структура проекта

```
index.html                        разметка приложения
styles.css                        оформление (без внешних шрифтов и зависимостей)
app.js                            интерфейс: состояние, кнопки, диалоги
src/encryptory-core.js            криптоядро (UMD: браузер + Node, один и тот же код)
tests/core.test.mjs               тесты ядра (node --test)
tools/cli.mjs                     командный интерфейс
tools/ui-smoke.mjs                смоук-тест интерфейса (необязательно, нужен jsdom)
tools/build-standalone.mjs        сборка в один HTML-файл
dist/encryptory-standalone.html   результат сборки (можно открыть двойным кликом)
```

Ядро не зависит от интерфейса: его можно подключать как обычный скрипт (`globalThis.EncryptoryCore`) или через `require` в Node.

## Разработка

```bash
npm test          # автотесты ядра (Node 20+, ничего устанавливать не нужно)
npm run cli -- selftest
npm run build     # пересобрать dist/encryptory-standalone.html

# необязательно: прогон настоящей страницы в jsdom (два «браузера», полный сценарий)
npm install --no-save jsdom && npm run test:ui
```

Зависимостей у самого приложения нет вообще: `npm install` не нужен, jsdom нужен только для необязательного смоук-теста интерфейса.

### CLI

```
node tools/cli.mjs keygen  [--name bob] [--out ./keys] [--pass «пароль»]
node tools/cli.mjs encrypt --key <приватный> [--pass «пароль»] --to <публичный: файл или строка>
                           [--text «…» | --in файл] [--out файл]
node tools/cli.mjs decrypt --key <приватный> [--pass «пароль»] [--text «…» | --in файл] [--out файл]
node tools/cli.mjs inspect [--text «…» | --in файл]     # от кого сообщение, без расшифровки
node tools/cli.mjs fingerprint --key <публичный>
node tools/cli.mjs selftest
```

Если не указать `--text` и `--in`, данные читаются со стандартного входа. Браузер и CLI используют один и тот же файл ядра, поэтому совместимы во всём: можно зашифровать в терминале и расшифровать в браузере.

## Хранение ключей

Приложение хранит ключи в `sessionStorage` вкладки: они переживают перезагрузку страницы, но исчезают при закрытии вкладки и никуда не отправляются. Постоянное хранение — это скачанный файл с приватным ключом, который вы держите у себя. Никаких cookie, аналитики, внешних запросов и CDN на странице нет — можно спокойно открыть её в офлайне.
